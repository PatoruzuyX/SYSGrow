**Verified improvements:** Ownership acquisition no longer implies permission to energize equipment. The proposed runtime starts inhibited, recovers outstanding operations, preserves quarantine independently of reservations and fails closed when recovery evidence is unavailable or corrupted.

These are appropriate target contracts.

**Remaining deficiency:** The checkpoint dependency graph permits EP-001 enforcement qualification at R2b, while R3a subsequently delivers durable recovery and quarantine. EP-001's own acceptance refinement requires those capabilities.

5. Exclusive process ownership exists, but safe physical-state recovery cannot be established.

**Required correction:** Explicitly distinguish minimum recovery containment from full recovery qualification. Either qualify all recovery invariants necessary for F-001 before R2b, or defer full F-001 closure until R3a/R3b and the final Q checkpoint.

### **G0-SS-02 — Scoped command authority, revocation and dispatch linearization**

Medium — partially corrected

**Pinned candidate evidence:** [FOUNDATION_BASELINE.md L75](https://github.com/PatoruzuyX/SYSGrow/blob/440bd0467eac17b5d2ee6f42760d84451756b4b1/docs/architecture/FOUNDATION_BASELINE.md?utm_source=chatgpt.com#L75), [REMEDIATION.md L100–102](https://github.com/PatoruzuyX/SYSGrow/blob/440bd0467eac17b5d2ee6f42760d84451756b4b1/docs/plans/REMEDIATION.md?utm_source=chatgpt.com#L100-L102).

The remaining issue is the boundary between durable admission, transport submission and delayed device delivery.

Conceptual command lifecycle. The actual protocol and linearization mechanism remain subject to design acceptance.

**Counterexample:** A command passes final admission, enters a transport queue, and its authorization expires before delivery. The application must not assume that revocation necessarily prevents delivery, nor may it silently treat the command as successfully completed.

**Required correction:** Require the accepted ADR and implementation plans to define the authoritative admission event, revocation ordering, transport submission boundary, expiry enforcement, fencing limitations and treatment of already-admitted commands. ## **6. EP-001–003 planning qualification**

### **EP-001 — Runtime ownership**

**Decision: HOLD.**

The proposed single control-capable process, shared operating-system lock and construction/activation separation are reasonable initial architectural choices for an edge-first application.

An OS lock alone cannot provide device-state recovery or revoke commands that have already entered an external transport.

The staged dependency requires correction before EP-001 closure can be planned unambiguously.

### **EP-002 — Runtime lifecycle**

**Decision: PASS at documentation-contract level, conditional on dependencies.**

The proposed lifecycle is coherent:

01

Stop admitting ordinary commands

02

Invalidate queued work

03

Account for in-flight physical effects

04

Reconcile device-specific state

05

Dispose runtime resources

06

Release ownership without losing quarantine

The plan correctly preserves independent protection and distinguishes process termination from graceful shutdown.

Dependency on EP-001 and EP-003 recovery contracts remains mandatory.

### **EP-003 — Actuator safety**

| Subplan | Assessment              | Required refinement                                                           |
| ------- | ----------------------- | ----------------------------------------------------------------------------- |
| EP-003A | HOLD                    | Explicit admission-to-transport failure and revocation semantics              |
| EP-003B | PASS — design direction | Preserve separate processing and physical certainty; qualify real composition |
| EP-003C | HOLD                    | Transactional authorization ordering and cancellation test oracles            |
| EP-003D | HOLD                    | Durable quarantine prerequisites and partial-operation recovery               |
| EP-003E | PASS — design direction | Device-specific eligibility and calibration validation                        |
| EP-003F | HOLD                    | Emergency authority, independent protection and rearm qualification           |

The separation into six bounded work packages is appropriate. I found no evidence requiring a wholesale rewrite of the actuator or irrigation subsystems.

The existing modular architecture can be preserved, provided these packages converge on one mandatory command-admission boundary and one coherent recovery contract.

## **8. Required safety architecture before activation**

The intended target architecture should preserve the following separation of responsibilities.

Reviewer-proposed conceptual contract, consistent with G0.1's edge-first direction. Not implemented architecture or an accepted ADR.

The critical architectural rule is that ownership, authorization and physical-state certainty are separate concerns.

A runtime can legitimately own the installation and still lack permission to operate a particular resource. Likewise, an authorized command can have an unknown physical outcome.

The system must preserve these distinctions throughout startup, normal execution, emergency intervention, shutdown and recovery.
